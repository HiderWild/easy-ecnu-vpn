## 1. 开放世界与真实错误

治理采用**开放世界和真实错误驱动**。未知或未建模状态本身绝不触发阻塞、强制核验、补偿、穷举或完整性证明。程序不可能也不需要遍历全部不确定结果；不得用少数已知允许状态组成白名单，再把其余状态一概解释成失败。只有已经真实发生、可观察的错误才进入处理：已观察到的具体错误类型应累积为精准分类；真实发生但原因未知的错误可以如实报告为未知，并向用户给出重试、重启、重装、日志反馈等当前可执行的下一步。未知错误不得自动扩张成长期全局门禁。

面向用户的错误必须讲清完整因果链：请求经过的层和模块、当时在做什么、发生了什么不应有的动作或结果、最终造成什么用户业务影响。已知原因应精确说明；原因尚不明确时应区分事实、推断和待观察方向，尽力给出可复现线索，但不得编造根因、来源或修复路径。

“尚未证明安全”、资格不能证明绝对可信、低概率对抗性文件系统风险或假设宿主机已经失陷，都不构成业务阻塞。只有已经观察到且能说明对当前流程有直接因果影响的具体危险、真实失败、无效运行环境或硬缺失依赖，才影响其直接依赖工作；不得长臂否决无关流程。定期倒查设计文档和需求文档，删掉基于绝对可信、完备状态空间或低概率对抗假设形成的过度安全设计。

禁止跨模块、跨系统、跨进程、跨宿主联合状态机用于执行、投影、诊断、验收或离线模型检查。该禁止不妨碍局部模块的有限状态校验，也不妨碍针对已有证据的具体疑难问题排查；两者都必须保持在明确模块和明确问题的边界内，不能伪装成全局完整性证明。

## 2. Common 边界与宿主优先次序

Common 是紧凑微内核种子，只承载明确平台无关的顶层业务逻辑、稳定契约、纯逻辑和小端口，不长臂规定宿主机制。明确跨宿主重叠的逻辑才进入 Common；不确定是否重叠的逻辑通过小端口留给宿主实现。宿主真实业务流优先：修复实际业务路径时，可以直接修 Common、共享构建、契约和测试，不必为了预先满足抽象层次而绕行。治理和证据权威仍受保护；宿主直修业务实现不等于可以改写规则、证据或结果来伪造通过。

### 单侧宿主优先的普通需求

普通需求的首次实现宿主可以任意选择且无需理由；选择宿主不受跨平台价值、风险预测、资格或另一宿主状态管辖，也不需要预声明复用。开始、继续或提交普通需求不以创建 Common 基底、规格、计划、manifest、Common 分支、另一宿主分支、另一宿主结果、路径白名单或专用推进记录为条件；失败、未运行或未知不阻塞不依赖它的开发。

当前宿主真实用户业务流跑通后，才可以被后续独立整合工作作为 Common 分析或候选迁移的正输入。它不自动决定 Common 归属，不自动接线、修改或宣称另一宿主通过，也不构成跨宿主状态机、白名单、专用登记或自动推进；后续独立整合工作仍自行判断归属与迁移，不得据此自动改变当前或另一宿主的实现、接线或通过结论。

若开发者选择留下宿主记录，记录只写观察事实、当前修补、当前活动接线和几句非约束整合建议，不能决定未来归属或另一宿主，也不得增加强制性的保留/摘出类型枚举。宿主的记录既不替专门整合工作作决定，也不为其他宿主预先定义机制；记录不是开始、继续或提交普通需求的条件。宿主修补应按可审计增量勤提交，使另一宿主能够借鉴已经发生的事实；提交身份本身仍不产生验收结论。

各宿主分别已经跑通的真实用户级业务流才是 Common 整合正输入。失败或未验证仅是缺陷证据，不是对开发或其他宿主的否决；专门整合分支或智能体独立决定是否收敛整合候选。若某一宿主对 Common 的修补幅度显著，应把它视为 Common 边界过宽或偏向单一平台的强证据，并同时评估两侧摘出对应逻辑；这是整合智能体需要核实的证据，不是自动归属结论，也不能由单侧宿主预先决定。候选形成后，必须回到相关原生宿主重跑真实流，不能以摘要、提交身份或离线推断代替该运行。

### 单侧宿主直修 Common 的诚实记录义务

单侧宿主为修复实际业务路径而修改 Common 时，须诚实记录三项内容：修改位置（文件、符号或契约）、目的（为何现有契约不足以承载该修复）、必要性（为何不能以宿主侧等价实现或绕行替代）。该记录随提交固化，供后续独立整合工作核实修补范围并构造新基线；记录本身不产生验收结论，也不替其他宿主或整合工作作决定，与本节关于记录不决定归属的既有表述一致。治理与证据权威仍受保护：直修业务实现不得通过改写规则、证据或结果来伪造通过。若某宿主对 Common 的修补幅度显著，仍视为 Common 边界过宽或偏向单一平台的强证据。

## 3. 双轨版本与重新接线

双轨版本可在普通目录长期共存，一个具体业务路径只接一版。未接线版本的文件头尾均须加入纯注释，明确：当前未接线、活动路径、文档链接、重新启用须重跑真实流。注释只说明当前事实，不产生删除、验收或阻塞效果。

不得用 #error、#warning 或 validator 逼删未接线版本。稳定多个 tag 后由开发者判断删除，无固定期限；删除决策应基于实际业务演进，而不是对未知状态的推断。

## 4. 测试、证据与脚本

每项改动同时采用模块测试和真实用户业务流测试：前者覆盖明确局部行为，后者在相应原生宿主确认用户实际路径。commit trailer、SHA、mock、模型或模块测试不能声明宿主真实通过；它们可以记录来源、复现条件或局部结果，但不能替代真实用户级运行。缺证据只禁止宣称通过，不阻塞开发。

固定流程脚本参数化，以 Requirement、宿主、业务流和可观察错误为输入；脚本的输出是当前运行事实，不得把未知输入扩张为穷举、跨宿主联合状态或自动否决。保留 No GitHub Actions：不得把 GitHub Actions 用作 CI、验收门禁或宿主真实业务流证据。

## 5. BusinessFlowMachine 的当前定位

当前产品 BusinessFlowMachine 仍接线，是宿主真实业务迁移的已知对象。本治理胶囊先撤销其治理、验收和离线穷举权：它可以继续服务当前接线的局部业务路径，但不能被解释为跨宿主、跨进程或跨系统的完整模型。不得谎称生产路径已退役；只有实际业务路径完成迁移、重新接线并在原生宿主跑通真实流后，才可更新该路径的事实说明。

## 6. 适用与冲突处理

本政策优先于旧的 Common-first、尾注、整合状态机和全局模型穷举式治理文字。遇到旧文档、历史记录或工具仍有相反描述时，把它们作为历史材料或待修复信号；活跃决策只按本文执行。具体局部故障排查可以增加临时观测和有限测试，但不得据此恢复本文禁止的联合状态机或未知状态门禁。
